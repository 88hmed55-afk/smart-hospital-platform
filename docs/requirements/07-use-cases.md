## UC-PAT-001 — تسجيل مريض جديد

| Field | Value |
|---|---|
| Actors | Receptionist (R-03) |
| Goal | إنشاء سجل مريض موحّد برقم طبي فريد |
| Preconditions | المستخدم مسجّل الدخول، لديه `PAT:CREATE`، الفرع مفتوح |
| Trigger | وصول مريض جديد للاستقبال |
| FR / BR | FR-PAT-001, FR-PAT-002, BR-PAT-001, BR-PAT-002, BR-PAT-005 |
| Postcondition | مريض جديد `ACTIVE` + رقم طبي + سجل تدقيق + (اختياري) بطاقة |

**Main Flow**
1. يفتح الاستقبال شاشة "مريض جديد".
2. يُدخل الاسم الكامل، الجنس، تاريخ الميلاد (أو العمر التقريبي)، الهاتف، الهوية إن وُجدت.
3. يُدخل جهة الاتصال الطارئة والعلاقة.
4. يضغط "تحقق من التكرار".
5. النظام يبحث في `patients` + `patient_identifiers` بمطابقة مرجّحة (اسم، ميلاد، هاتف، هوية).
6. النظام يعيد `NO_MATCH`.
7. يُدخل العنوان والملاحظات ويحفظ.
8. النظام يولّد `public_id` (ULID) ورقمًا طبيًا متسلسلًا، ويحفظ داخل معاملة.
9. يعرض بطاقة المريض مع الرقم الطبي وخيار الطباعة.

**Alternatives**
- 5a. `EXACT_MATCH` (هوية وطنية مطابقة) ⇒ رفض الإنشاء وعرض السجل الموجود.
- 5b. `POSSIBLE_MATCH` ⇒ عرض قائمة مشابهة؛ المستخدم يختار "فتح السجل" أو "متابعة التسجيل".
- 7a. متابعة التسجيل مع `POSSIBLE_MATCH` تتطلب `PAT:OVERRIDE` + سبب ≥ 15 حرفًا.
- 4a. عمر تقريبي فقط ⇒ يُخزَّن `birth_date_estimated=true`.

**Exceptions**
- E1: فشل DB ⇒ لا رقم طبي محجوز، رسالة خطأ، لا سجل جزئي.
- E2: محاولة إدخال تاريخ ميلاد مستقبلي ⇒ رفض على الحقل.
- E3: جلسة منتهية ⇒ 401 وإعادة توجيه للدخول مع الحفاظ على المدخلات (بلا بيانات حساسة في التخزين المحلي).

## UC-PAT-002 — دمج سجلات مريض مكرر

| Field | Value |
|---|---|
| Actors | HOSP_ADMIN (R-02) يعتمد، AUDITOR (R-16) يراجع |
| Preconditions | سجلان مؤكدان لنفس الشخص، سبب موثّق |
| FR / BR | FR-PAT-004, BR-PAT-004, BR-PAT-008 |
| Postcondition | سجل أساسي واحد، السجل الآخر `MERGED`, كل المراجع محوّلة، أثر كامل |

**Main Flow**
1. يفتح المسؤول "دمج المرضى" ويختار السجل الأساسي والثانوي.
2. النظام يعرض مقارنة: الزيارات، الفواتير، الوصفات، المرفقات.
3. يعرض تعارضات محتملة (نفس الموعد، نفس الفاتورة).
4. يُدخل سبب الدمج ويؤكد.
5. النظام ينشئ `patient_merges` وينقل المراجع (`patient_id` → الأساسي) داخل معاملة.
6. يضع `merged_into_id` على الثانوي ويعطّله.
7. يسجّل `audit_log` + إشعار للمدقق.

**Alternatives**
- 3a. تعارض فاتورتين لنفس الخدمة ⇒ يتوقف الدمج ويُطلب قرار مالي.

**Exceptions**
- E1: فشل منتصف النقل ⇒ Rollback كامل، لا سجل نصف مدموج.
- E2: محاولة دمج سجل له Break-Glass نشط ⇒ رفض حتى انتهائه.

## UC-SCH-001 — حجز موعد

| Field | Value |
|---|---|
| Actors | Receptionist, Doctor |
| Preconditions | طبيب مفعّل + جدول + خدمة/عيادة |
| FR / BR | FR-SCH-001..003, BR-SCH-001..003, BR-SCH-008 |
| Postcondition | موعد `SCHEDULED` + إشعار اختياري |

**Main Flow**
1. يبحث عن المريض ويختار العيادة/الطبيب.
2. يعرض النظام الفترات المتاحة 14 يومًا قادمة.
3. يختار فترة ويؤكد.
4. النظام يتحقق: الطبيب مفعّل، الفترة داخل الجدول، لا تعارض، لا عطلة.
5. ينشئ `appointment` بحالة `SCHEDULED`.
6. يعرض تأكيدًا مع رقم الموعد وخيار طباعة/إرسال.

**Alternatives**
- 2a. لا فترات ⇒ اقتراح أقرب طبيب/تاريخ بديل.
- 3a. تجاوز الحد ⇒ يتطلب `SCH:OVERBOOK` + سبب.
- 4a. تعارض لحظي (سباق) ⇒ 409 مع إعادة عرض الفترات.

**Exceptions**
- E1: مريض غير موجود ⇒ تحويل إلى UC-PAT-001.

## UC-EMR-001 — زيارة عيادة وتوثيق طبي

| Field | Value |
|---|---|
| Actors | Doctor |
| Preconditions | مريض موجود، موعد/وصول، طبيب لديه `EMR:CREATE` |
| FR / BR | FR-EMR-001..006, BR-EMR-001..005 |
| Postcondition | زيارة `CLOSED` + ملاحظة موقّعة + تشخيص + طلبات |

**Main Flow**
1. يفتح الطبيب قائمة مرضاه/الطابور.
2. يفتح زيارة جديدة (أو يكمل زيارة قائمة).
3. يراجع التنبيهات: حساسيات، أمراض مزمنة، نتائج حديثة.
4. يسجّل الشكوى والتاريخ المرضي والفحص السريري.
5. يسجّل/يراجع العلامات الحيوية.
6. يضيف تشخيصًا أساسيًا (ورمز اختياري).
7. ينشئ طلب مختبر/أشعة و/أو وصفة.
8. يكتب الخطة والملاحظات ويوقّع.
9. يغلق الزيارة بعد تحقق الحد الأدنى.

**Alternatives**
- 4a. استخدام قالب توثيق/Order Set ⇒ تعبئة مسبقة قابلة للتعديل.
- 6a. تشخيص غير موجود في الكتالوج ⇒ إدخال نصي مع وسم `unmapped`.
- 9a. طلبات معلّقة بلا قرار ⇒ تحذير مع إمكانية الإغلاق بصلاحية.

**Exceptions**
- E1: محاولة توقيع بلا تشخيص ⇒ رفض (حسب إعداد `require_diagnosis`).
- E2: محاولة تعديل بعد التوقيع ⇒ إنشاء Amendment.

## UC-LAB-003 — إدخال واعتماد نتيجة

| Field | Value |
|---|---|
| Actors | Lab Technician (إدخال), Lab Supervisor (اعتماد) |
| Preconditions | عينة `RECEIVED` |
| FR / BR | FR-LAB-005, FR-LAB-006, BR-LAB-004, BR-LAB-007 |
| Postcondition | نتيجة `VERIFIED` + إشعار للطبيب + TAT |

**Main Flow**
1. يفتح الفني العينة ويختار الفحص.
2. يُدخل القيمة/النتيجة النصية.
3. النظام يقارن بالمدى المرجعي ويضع `LOW/HIGH/CRITICAL`.
4. يحفظ كـ `RESULTED` (غير معتمد).
5. المشرف يراجع القيم والسياق ويضغط "اعتماد".
6. النظام يتحقق من الصلاحية و`dual_control` إن فُعّل.
7. ينقل الحالة إلى `VERIFIED` ثم `RELEASED`، ويحسب TAT.
8. يُنشئ حدث Outbox لإشعار الطبيب.
9. إذا `CRITICAL` ⇒ إشعار Critical + تسجيل في `critical_value_alerts`.

**Exceptions**
- E1: اعتماد بلا مراجعة ⇒ 403.
- E2: قيمة غير رقمية لفحص رقمي ⇒ رفض.
- E3: فشل إشعار ⇒ النتيجة محفوظة، الإشعار في Outbox.

## UC-PHR-002 — صرف وصفة (FEFO)

| Field | Value |
|---|---|
| Actors | Pharmacist |
| Preconditions | وصفة `SIGNED`/`REVIEWED`، مخزون كافٍ |
| FR / BR | FR-PHR-003..007, BR-PHR-002..007 |
| Postcondition | `dispensing_transaction` + حركات مخزون + وصفة `DISPENSED` |

**Main Flow**
1. يفتح الصيدلي الطابور ويمسح/يبحث عن الوصفة.
2. يراجع المريض، الحساسية، الجرعة، التفاعلات.
3. يوافق على المراجعة (`REVIEWED`).
4. يضغط "صرف".
5. النظام يقفل الدفعات الصالحة (FEFO) ويخصم الكميات.
6. ينشئ `dispensing_transactions` + `stock_movements` سالبة.
7. يحدّث حالة الوصفة/البنود.
8. ينشئ بند فاتورة إن كانت السياسة `charge_on_dispense`.
9. يطبع ملصق الدواء (اسم، جرعة، تعليمات، باركود).

**Alternatives**
- 2a. رفض المراجعة بسبب ⇒ وصفة `REJECTED` مع سبب، إشعار للطبيب.
- 5a. نقص كمية ⇒ صرف جزئي `PARTIALLY_DISPENSED` مع المتبقي.
- 5b. تجاوز FEFO (دفعة أقرب صلاحية محجوزة) ⇒ يتطلب `PHR:FEFO_OVERRIDE` + سبب.

**Exceptions**
- E1: دفعة انتهت بين العرض والتنفيذ ⇒ إعادة اختيار تلقائية أو رفض.
- E2: فشل أي خطوة ⇒ Rollback كامل، لا خصم بلا صرف.
- E3: طلب مكرر (Double click) ⇒ Idempotency Key يمنع التكرار.

4. يطبّق خصمًا إن كان مخوّلًا (سبب + حد).
5. يؤكد الإصدار: رقم فاتورة، إجمالي، رصيد.
6. يطبع/يعرض.

**Alternatives**
- 3a. خدمة منفذة مرتين بالخطأ ⇒ لا تُضاف مرتين؛ تُصحح من مصدرها.

## UC-BIL-002 — تسجيل دفعة

| Field | Value |
|---|---|
| Actors | Cashier |
| Preconditions | فاتورة `ISSUED`/`PARTIALLY_PAID` |
| FR / BR | FR-BIL-004, FR-BIL-005, BR-BIL-004, BR-BIL-005 |
| Postcondition | `payment` + إيصال + رصيد محدّث |

**Main Flow**
1. يفتح الفاتورة ويعرض الرصيد.
2. يُدخل المبلغ وطريقة الدفع ومرجعًا.
3. النظام يتحقق: مبلغ > 0، ≤ الرصيد (أو Prepayment)، `idempotency_key` جديد.
4. ينشئ الدفعة، يحدّث حالة الفاتورة، يولّد رقم إيصال.
5. يطبع الإيصال.

**Alternatives**
- 3a. مفتاح مكرر ⇒ يعيد نفس الإيصال ولا ينشئ دفعة.
- 3b. مبلغ > الرصيد ⇒ رفض أو تحويل إلى رصيد مقدم حسب السياسة.

## UC-BIL-003 — استرداد

| Field | Value |
|---|---|
| Actors | Cashier (طلب), Finance Manager (اعتماد) |
| Preconditions | دفعة موجودة |
| FR / BR | FR-BIL-006, BR-BIL-006, SOD-03 |
| Postcondition | `refund` + إيصال + رصيد محدّث + اعتماد |

**Main Flow**
1. يختار الدفعة الأصلية والسبب والمبلغ.
2. النظام يتحقق: المبلغ ≤ المتبقي القابل للاسترداد.
3. يُنشئ طلب استرداد `PENDING_APPROVAL`.
4. المدير المالي يعتمد أو يرفض بسبب.
5. عند الاعتماد: `refund` + حركة مالية + إشعار.

## UC-ER-001 — استقبال وفرز حالة طارئة

| Field | Value |
|---|---|
| Actors | Triage Nurse, ER Doctor |
| Preconditions | وصول حالة طارئة |
| FR / BR | FR-ER-001..004, BR-ER-001..003 |
| Postcondition | حالة طوارئ + مستوى فرز + وقت انتظار |

**Main Flow**
1. تسجيل سريع: جنس، عمر/مجهول، شكوى مختصرة.
2. قياس العلامات الحيوية الأساسية.
3. اختيار مستوى الفرز من القائمة المعتمدة.
4. النظام يضيفه للوحة الطوارئ ويحسب `arrival_at`.
5. الطبيب يبدأ التقييم ⇒ `first_assessment_at` وزمن الانتظار.
6. قرار: علاج/تنويم/تحويل/خروج.

**Alternatives**
- 3a. مريض غير قادر على التواصل ⇒ تسجيل مجهول مع رقم مؤقت.
- 6a. مغادرة قبل التقييم ⇒ LWBS مع الوقت.

## UC-DEC-001 — مراجعة واعتماد بطاقة قرار

| Field | Value |
|---|---|
| Actors | Dept Manager (مراجعة), HOSP_ADMIN (اعتماد) |
| Preconditions | بطاقة `DETECTED` بأدلة كافية |
| FR / BR | FR-DEC-002..007, BR-DEC-002..006 |
| Postcondition | قرار `APPROVED`/`REJECTED`/`DEFERRED` + أثر لاحق |

**Main Flow**
1. يفتح المدير البطاقة: المشكلة، الأدلة، خط الأساس، التحليل، التوصية، الأثر المتوقع، الثقة، الافتراضات، القيود.
2. يطلب بيانات إضافية أو يناقش.
3. يوصي بالقبول/الرفض/التأجيل مع سبب.
4. المسؤول المخوّل يعتمد.
5. تُسجَّل خطة التنفيذ والمسؤول والتاريخ.
6. بعد التنفيذ: تُقاس نفس KPI في نفس النافذة وتُقارن.

**Exceptions**
- E1: عينة < الحد الأدنى ⇒ البطاقة تُغلق `INSUFFICIENT_DATA`.
- E2: محاولة تنفيذ آلي ⇒ ممنوع (BR-DEC-003).
