## 1. الرؤية (Vision Statement)

> أن يصبح **Smart Hospital** نظامًا مؤسسيًا واحدًا يربط كل لحظة في رحلة المريض — من الاستقبال إلى الخروج — بمصدر بيانات واحد، وقواعد عمل واضحة، ورؤية تشغيلية تساعد الإدارة على اتخاذ قرار مبني على دليل، دون أن يستبدل الحكم الطبي البشري.

النظام ليس "تطبيق CRUD للمرضى". هو **منصة تشغيل مؤسسية** يكون فيها:

- لكل مريض **هوية واحدة** ورقم طبي واحد وسجل واحد.
- لكل عملية طبية أو مالية **مسار حالة واضح** لا يقبل الانتقال العشوائي.
- لكل دواء أو عينة أو سرير أو دفعة **تتبّع مركزي** يمنع الازدواج.
- لكل وصول إلى سجل طبي **أثر تدقيق**.
- لكل رقم إداري **تعريف حسابي** ومصدر بيانات وتاريخ تحديث.

## 2. المشكلة (Problem Statement)

المستشفيات التي تعمل بأوراق أو أنظمة منفصلة تعاني من مشكلات مترابطة، ليست كل واحدة منها "مشكلة برمجية" مستقلة:

| المشكلة | السبب الجذري | الأثر التشغيلي |
|---|---|---|
| تشتّت بيانات المريض | لا يوجد معرّف موحد | تكرار الفحوصات والأدوية |
| تكرار التسجيل | إدخال يدوي في كل قسم | سجلات مزدوجة وتقارير مضللة |
| ضعف الوصول للتاريخ الطبي | أنظمة معزولة | قرارات علاجية بلا سياق |
| تعارض المواعيد والانتظار | جدولة غير محكومة بقواعد | إزعاج المرضى وهدر وقت الأطباء |
| تأخر نتائج المختبر | لا تتبّع لمراحل العينة | تأخر العلاج وطول الإقامة |
| انفصال الطبيب/المختبر/الصيدلية | لا أحداث مشتركة | وصفات لا تُصرف، نتائج لا تُقرأ |
| ضعف إدارة الأسرة | لوحة أسرة ورقية | تنويم في الممرات أو أسرة فارغة |
| انفصال الخدمة عن الفاتورة | لا Charge Capture | فقد إيراد أو فواتير خاطئة |
| ضعف رقابة المخزون | لا دفعات ولا FEFO | انتهاء صلاحية ونقص مفاجئ |
| غياب مؤشرات الأداء | لا تعريفات KPI | قرارات إدارية بالانطباع |
| ضعف أمن السجلات | صلاحيات على الواجهة فقط | وصول غير مصرح غير مكتشف |

**الفرضية الأساسية:** أغلب هذه المشكلات ليست مشكلات "تخزين"، بل مشكلات **هوية، وحالة، وأحداث، وصلاحيات**. لذلك بُني التصميم حول هذه المفاهيم الأربعة.

## 4. الأهداف القابلة للقياس (Objectives)

كل هدف مرتبط بمؤشر وطريقة قياس. الأرقام **أهداف تصميمية** تُعاير بعد القياس الفعلي (انظر `ASM-020`).

| # | الهدف | مقياس النجاح | كيف يُقاس |
|---|---|---|---|
| OBJ-01 | هوية مريض واحدة | 0 سجل مريض مكرر مؤكد بعد المراجعة | تقرير `patient_merge_candidates` + مراجعة عينة |
| OBJ-02 | ربط الخدمة بالفاتورة | ≥ 98% من الخدمات المنفذة لها بند فاتورة | استعلام مطابقة `service_execution` ↔ `invoice_item` |
| OBJ-03 | سلامة الصرف | 0 صرف من دفعة منتهية أو كمية سالبة | قيود DB + تقرير تدقيق |
| OBJ-04 | تتبّع العينة | 100% من العينات لها سلسلة أحداث كاملة | `lab_sample_events` |
| OBJ-05 | عدم تعارض الأسرة | 0 تداخل زمني في `bed_assignments` | قيد Unique + اختبار تزامن |
| OBJ-06 | وصول غير مصرح | 0 وصول ناجح بدون صلاحية | Security tests + `access_logs` |
| OBJ-07 | موثوقية الإشعارات | 0 نتيجة مختبر مفقودة بسبب فشل إشعار | Outbox DLQ = 0 في اختبار الفشل |
| OBJ-08 | استمرارية LAN | النظام يعمل بالكامل عند قطع الإنترنت الخارجي | Network test |
| OBJ-09 | قابلية النقل | نشر نفس EAR في بيئة ثانية بتغيير إعدادات فقط | Deployment test |
| OBJ-10 | شفافية التحليلات | 100% من KPIs لها تعريف ومصدر ومالك | KPI Catalog review |

## 5. نطاق النظام (System Scope)

### 5.1 داخل النطاق — النسخة الأولى

- تسجيل المرضى وهوية موحدة وكشف تكرار.
- مواعيد وجدولة واستقبال وطوابير.
- زيارة عيادة، سجل طبي، تشخيصات، علامات حيوية، ملاحظات، خطط علاج.
- طلبات مختبر ودورة عينة ونتائج واعتماد وتصحيح.
- وصفات وصرف صيدلي ودفعات وصلاحية ومخزون دوائي.
- تنويم وأسرة ونقل وخروج.
- فواتير وبنود ومدفوعات واستردادات.
- مخزون ومشتريات مبسطة.
- مستخدمون وأدوار وصلاحيات وتدقيق.
- إشعارات (Outbox/JMS/SSE).
- تقارير وKPIs وبطاقات قرار تشغيلية.
- إدارة إعدادات المستشفى (اسم، شعار، عملة، أقسام، خدمات، أسعار).

### 5.2 داخل النطاق — مُصمّم لكن مؤجّل التنفيذ

- الأشعة (Orders + Reports + جدولة، دون PACS).
- غرف العمليات (جدولة + Checklist + سجل إجراء).
- موارد بشرية (موظفون، مناوبات، تراخيص).
- وحدة الجودة وسلامة المرضى (Incident Reporting).
- التمريض المتقدم (خطة رعاية، إعطاء دواء بالباركود).

### 5.3 خارج النطاق — النسخة الأولى

| Outside | السبب | البديل |
|---|---|---|
| تشخيص طبي آلي أو وصفة آلية | خطر سريري وقانوني | قواعد تحقق فقط |
| التأمين والمطالبات | تعقيد دورة إيراد كاملة | نقدي فقط، جدول `payer` جاهز |
| Blood Bank | تنظيم واعتماد خاص | تصميم جدول مستقبلي فقط |
| PACS / DICOM viewer | منتج مستقل | رابط لملف التقرير + حقل `study_uid` |
| بوابة المريض / Telemedicine | نطاق منتج آخر | API جاهز للتوسع |
| Multi-branch كامل | تعقيد إداري | `branch_id` موجود، منطق v1 لمستشفى واحد |
| HA / Clustering / Load Balancing | يحتاج دراسة واختبار | خادم واحد + RTO/RPO |
| Mobile App | تكلفة مضاعفة | PWA متجاوب |
| Payroll كامل | نظام منفصل | بيانات توظيف فقط |
| فاتورة إلكترونية/ضرائب محلية | يعتمد على بلد | قالب قابل للتهيئة |

## 6. مبادئ التصميم الملزمة

| # | المبدأ | الترجمة العملية |
|---|---|---|
| DP-01 | **Single Source of Truth** | كل بيانات المريض في قاعدة واحدة، لا نسخ محلية |
| DP-02 | **Identity before Data** | لا يُنشأ سجل طبي قبل التحقق من هوية المريض |
| DP-03 | **State over Status Flags** | آلات حالة صريحة، لا أعمدة `is_done` متفرقة |
| DP-04 | **Append-only Clinical Truth** | التصحيح بنسخة جديدة، لا تعديل يمحو التاريخ |
| DP-05 | **Money is Derived** | الرصيد مشتق من الحركات، لا يُكتب يدويًا |
| DP-06 | **Permission at the Service** | التفويض في EJB، لا في React |
| DP-07 | **Fail Closed** | أي فشل تحقق/صلاحية = رفض، لا سماح |
| DP-08 | **Explainable by Default** | كل رقم وكل توصية لها تعريف ومصدر ودرجة ثقة |
| DP-09 | **Configuration not Code** | اسم المستشفى، الأسعار، الأقسام، القوالب = إعدادات |
| DP-10 | **No Silent Success** | لا رسالة نجاح إلا بعد Commit فعلي |
| DP-11 | **Measure before Optimize** | لا فهارس ولا تخزين مؤقت قبل قياس |
| DP-12 | **Human in the Loop** | كل قرار حساس يحتاج موافقة بشرية مخولة |

## 7. قيود المشروع (Constraints)

| # | القيد | الأثر على التصميم |
|---|---|---|
| CST-01 | Jakarta EE 10 فقط، لا Spring | كل الحقن عبر CDI/EJB، REST عبر Jakarta REST |
| CST-02 | GlassFish 7 Full Platform | JMS/MDB/Timer متاحة أصلًا، لا middleware إضافي |
| CST-03 | MySQL 8.0.38 | لا ميزات خاصة بـ PostgreSQL (مثل Exclusion Constraints) |
| CST-04 | Apache Ant + NetBeans 21 | هيكل مشاريع NetBeans إلزامي |
| CST-05 | JDK 17 | لا استخدام ميزات Java 21 |
| CST-06 | خادم واحد مبدئيًا | التصميم يفصل منطقيًا بين App وDB |
| CST-07 | LAN فقط، لا اعتماد على إنترنت | لا خطوط Google Fonts/CDN في الإنتاج |
| CST-08 | العربية RTL أساسًا | كل مكوّن واجهة يجب أن يعمل في الاتجاهين |
| CST-09 | بيانات وهمية فقط | لا بيانات مرضى حقيقية في التطوير أو العرض |
| CST-10 | نطاق أكاديمي بزمن محدود | قصّ صريح للنطاق في `11` |

## 8. تعريف النجاح النهائي (Definition of Done)

النظام يُعتبر "مكتملًا" فقط عند تحقق **الخمسة معًا**:

1. **تقنيًا:** EAR يُبنى بـ Ant، يُنشر على GlassFish 7 نظيف، ويعمل على JDK 17.
2. **وظيفيًا:** سيناريو E2E كامل: تسجيل → موعد → زيارة → طلب مختبر → نتيجة معتمدة → وصفة → صرف → فاتورة → دفع → تقرير.
3. **مؤسسيًا:** معاملات صحيحة، أقفال تزامن، تدقيق، Outbox، صلاحيات backend.
4. **ذكيًا:** KPIs معرّفة + 6 بطاقات قرار + قياس أثر فعلي.
5. **تشغيليًا:** تركيب على خادم نظيف، وصول من جهاز قسم عبر LAN، HTTPS، نسخ احتياطي واستعادة مُختبرة، وقطع إنترنت خارجي لا يوقف العمل.
