> **الغرض:** تحويل 166 متطلبًا إلى **نطاق قابل للتسليم**. التصنيف هنا ليس "رأيًا"، بل قاعدة: كل ما هو `Core` يجب أن يعمل ويُختبر، وكل ما هو `Extended` يُصمّم ويُنفّذ جزئيًا، وكل ما هو `Future` يُوثّق ولا يُبنى.

## 1. مستويات النطاق الثلاثة

| المستوى | التعريف | ما يُسلَّم | معيار القبول |
|---|---|---|---|
| **Core** | وظائف لا يعمل المستشفى بدونها يوميًا | كود + قاعدة بيانات + شاشات + اختبارات + تدريب | كل `Must` في النطاق + اجتياز TC المرتبطة |
| **Extended** | وظائف مهمة لكن يمكن تشغيل المستشفى بدونها في الإصدار الأول | تصميم كامل + جداول + عقود API + تنفيذ جزئي حسب الوقت | التصميم مكتمل ومتّسق، والتنفيذ لا يكسر Core |
| **Future** | وظائف خارج v1 بقرار واعٍ | وثيقة تصميم موجزة + نقاط توسّع في الكود | لا كود إنتاجي، ولا ادعاء توفّر |

**قاعدة صارمة:** لا تُخلط وظيفة `Future` داخل شاشة `Core` بشكل يوحي بأنها تعمل. أي عنصر غير منفّذ يظهر معطّلًا مع وسم **"غير متاح في v1"**، لا بشكل صامت.

## 3. نطاق النسخة الأكاديمية (MVP)

### 3.1 داخل MVP — إلزامي

| النطاق | ما يُنفّذ فعليًا | لماذا في MVP |
|---|---|---|
| SYS | إعدادات المستشفى، الهيكل، الخدمات والأسعار، أيام العمل | كل شاشة تحتاج هذه البيانات |
| IAM | دخول، أدوار، صلاحيات، نطاق بيانات، جلسات، تدقيق دخول | يثبت أن النظام مؤسسي لا تجريبي |
| PAT | تسجيل، منع تكرار، بحث، بطاقة، حساسيات، Timeline | أساس السيناريو |
| SCH | جداول، حجز، منع تعارض، Check-In، قائمة انتظار | يربط الاستقبال بالعيادة |
| EMR | زيارة، توثيق، علامات حيوية، تشخيص، وصفة، طلب مختبر، توقيع، إغلاق | جوهر العرض الأكاديمي |
| LAB | كتالوج، طلب، عينة، نتيجة، اعتماد، تصحيح، TAT | سلسلة مخبرية كاملة قابلة للاختبار |
| PHR | كتالوج، وصفة، مراجعة، صرف FEFO، مخزون، إرجاع | أثبت أصعب منطق تزامن |
| ADT | طلب تنويم، سرير، نقل، خروج، لوحة أسرة | يثبت إدارة الموارد |
| BIL | Charge Capture، بنود، دفع، Idempotency، إيصال، إقفال | يثبت السلامة المالية |

| RPT | تقارير مرضى/زيارات/إشغال/تحصيل + تصدير | مخرج إداري ملموس |

**إجمالي MVP:** 122 FR (منها 94 `Must`) موزعة على 13 نطاقًا.

### 3.2 امتداد داخل MVP — يُنفّذ إن سمح الجدول

| النطاق | الحد الأدنى | لماذا ليس إلزاميًا |
|---|---|---|
| ER | وصول سريع + فرز بقالب + لوحة | يحتاج بروتوكول فرز معتمدًا (ASM-016) |
| NUR | قائمة جناح + علامات حيوية + ملاحظات | يمكن تغطيتها مؤقتًا داخل EMR |
| INV | كتالوج + استلام + صرف + منع رصيد سالب | الصيدلية تغطي الحد الأدنى للدفعات |

**إجمالي الامتداد:** 22 FR (منها 14 `Must`). القرار: يُنفّذ بالترتيب بعد اكتمال MVP، ولا يُؤجَّل أي `Must` من MVP لأجله.

### 3.3 تصميم فقط — لا تنفيذ

| النطاق | يُسلَّم | لا يُسلَّم |
|---|---|---|
| RAD | ERD، API، حالات، قوالب تقارير | شاشات إنتاجية، PACS، DICOM |
| ORS | ERD، API، حالات، قائمة سلامة قابلة للتهيئة | جدولة عمليات فعلية |
| HRM | ERD مبسّط، بيانات طبيب/ترخيص | رواتب، حضور، تقييم أداء |
| INT | واجهات Adapter، جداول رسائل، معرفات خارجية | أي ادعاء توافق FHIR/HL7 |

## 5. تطبيق MoSCoW

| الأولوية | المعنى | الالتزام |
|---|---|---|
| **M** | لا يعمل النظام بدونه | يُسلَّم ويُختبر، ولا يُؤجَّل |
| **S** | مهم، وله بديل مؤقت | يُسلَّم إن لم يهدد MVP |
| **C** | تحسين | يُصمَّم فقط، ويُنفَّذ في v1.1 |
| **W** | لن يُنفَّذ | موثّق كخارج نطاق |

**قواعد الحسم عند ضيق الوقت:**

1. لا يُحوَّل `M` إلى `S` إلا بقرار موثّق من المالك (Change Request).
2. يُحوَّل `S` إلى `C` تلقائيًا عند تجاوز بوابة المرحلة بـ > 20% (RSK-001 trigger).
3. لا يُضاف أي `C` قبل اجتياز كل `M` في نفس النطاق.
4. أي `M` جديد يدخل بعد الاعتماد يتطلب حذف `M` آخر أو تمديد الجدول — لا "إضافة مجانية".

## 6. تعريف الإنجاز (Definition of Done) لكل مستوى

### Core
- [ ] FR منفّذ في EJB + API + شاشة.
- [ ] BR المرتبطة مفروضة في الخدمة و/أو DB.
- [ ] صلاحية ونطاق بيانات مطبّقان ومُختبران لدورين على الأقل.
- [ ] TC المرتبط ناجح (إيجابي + سلبي + تزامن إن وُجد).
- [ ] سجل تدقيق للأحداث الحساسة.
- [ ] ترجمة عربية + إنجليزية للمصطلحات.
- [ ] توثيق API ومخطط البيانات محدّث.
- [ ] لا أخطاء Critical/High مفتوحة.

### Extended
- [ ] ERD + قاموس بيانات + قيود.
- [ ] عقود API + حالات + صلاحيات.
- [ ] تصميم شاشات أو Prototype.
- [ ] لا كسر لأي Core، ولا اعتماد عكسي.
- [ ] وسم واضح "غير منفّذ في v1" إن لم يُنفّذ.

### Future
- [ ] فقرة تصميم + نقطة توسّع (Interface/Adapter).
- [ ] لا جداول إنتاجية ولا شاشات.
- [ ] لا ادعاء توفّر في العرض أو الوثائق التسويقية.

## 7. إدارة تغيير النطاق

| الحالة | الإجراء | الجهة |
|---|---|---|
| إضافة `M` جديدة | Change Request + حذف/تأجيل مقابل + تحديث الجدول | المالك + المعمارية |
| تحويل `M` إلى `S` | قرار موثّق + تحديث `03` و`11` و`roadmap/01` | المالك |
| إضافة وحدة Extended | تصميم فقط أولًا + تقدير أثر | المعمارية |
| طلب ميزة Future | تُسجَّل في Backlog v2، لا تُناقش في Sprint | مدير المنتج |

**البوابة:** لا يبدأ تنفيذ أي طلب نطاق جديد قبل تحديث هذا الملف وتوقيع المالك. هذا يمنع "تضخم النطاق" (RSK-001).
