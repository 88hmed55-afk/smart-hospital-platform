# 04 — Backup & Recovery

**نسخ احتياطي مُختبر، استعادة مُثبتة، وRPO/RTO قابلان للقياس — لا نسخة بلا استعادة**

| Field | Value |
|---|---|
| Document ID | DEP-BKP-001 |
| Version | 0.1 |
| Status | Approved (baseline 0.1) |
| RPO | ≤ 15 دقيقة (هدف فعلي ≤ 5 دقائق مع Binlog كل 5 دقائق) |
| RTO | ≤ 4 ساعات |
| Related | `01-server-architecture.md`, `03-installation.md`, `05-monitoring-operations.md`, NFR-REL-007/008, NFR-PRV-004, NFR-OPS-005/006 |

---

## 1. المبادئ

1. **3-2-1:** 3 نسخ، وسيطان مختلفان، نسخة خارج الموقع/خارجه عن الخادم.
2. **مشفّرة دائمًا:** النسخة بلا تشفير = خطر. المفتاح ليس مع النسخة.
3. **غير قابلة للتعديل:** النسخة اليومية على NAS immutable/append-only إن أمكن.
4. **مُختبرة دوريًا:** نسخة لم تُستعد = نسخة غير موجودة.
5. **استعادة بأقل صلاحية:** من يستعيد لا يملك بالضرورة صلاحية تعديل الإنتاج.
6. **كل عملية موثّقة:** من، ماذا، متى، لماذا، والنتيجة.

---

## 2. نطاق النسخ

| المكوّن | المحتوى | الأهمية | التكرار |
|---|---|---|---|
| MySQL — Full | كل الجداول + Routines + Triggers + Events | حرجة | يومي |
| MySQL — Binlog | كل التغييرات بعد Full | حرجة | كل 5–15 دقيقة |
| إعدادات التطبيق | `application.properties`, `secrets.env` | حرجة | عند كل تغيير + يومي |
| EAR / Releases | حزمة النشر والنسخ السابقة | عالية | عند كل إصدار |
| Migrations | SQL + Ant + checksums | عالية | عند كل تغيير |
| المرفقات | `attachments` + ملفات `storage_key` | عالية | يومي (Incremental) |
| Nginx / TLS | Config + الشهادات (بلا مفاتيح خاصة إن أمكن) | عالية | عند كل تغيير |
| سجلات التدقيق | `audit_logs` (جزء من DB) | حرجة | مع Full + أرشيف سنوي |
| التوثيق التشغيلي | Runbooks + خطة الشبكة | متوسطة | عند كل تغيير |

**لا يُنسخ:** ملفات مؤقتة، Cache، Logs التطبيق (إلا عند تحقيق)، بيانات اعتماد في Git.

## 3. استراتيجية النسخ

### 3.1 قاعدة البيانات

| الحجم | الطريقة | ملاحظة |
|---|---|---|
| ≤ 20 GB | `mysqldump --single-transaction --routines --triggers --events` | بسيطة ومحمولة |
| > 20 GB | Percona XtraBackup (Full + Incremental) | أسرع وأقل إجهادًا |
| أي حجم | Binlog Shipping كل 5 دقائق | يحقق RPO |

**قاعدة:** `--single-transaction` إلزامي مع InnoDB لتفادي قفل الكتابة. لا `--lock-all-tables` في الإنتاج.

### 3.2 الجدول الزمني

| الوقت | المهمة | الوجهة | الاحتفاظ |
|---|---|---|---|
| 01:00 | Full DB | NAS `/backups/db/full/` | 14 يومي + 8 أسبوعي + 12 شهري |
| كل 5 دقائق | Binlog Ship | NAS `/backups/db/binlog/` | 14 يومًا |
| 01:30 | مرفقات (Incremental) | NAS `/backups/files/` | 30 يومًا + شهري |
| 02:00 | Config + EAR + Migrations | NAS `/backups/app/` | 10 إصدارات |
| أسبوعيًا (أحد) | نسخة Offline/Offsite | قرص مشفّر/خزن خارجي | 8 أسابيع |
| شهريًا | أرشيف تدقيق | NAS `/backups/audit/` | 7 سنوات |
| ربع سنوي | تمرين استعادة كامل | STAGING | تقرير |

**الاحتفاظ الكلي:** لا يقل عن 14 يومًا للاستعادة السريعة، و12 شهرًا للاستعادة التاريخية، و7 سنوات للتدقيق حسب السياسة.

### 3.3 التشفير والمفاتيح

| البند | القرار |
|---|---|
| التشفير | Restic (AES-256) أو GPG للـ dumps |
| المفتاح | في خزنة كلمات مرور/HSM/مغلف مغلق، ليس على الخادم |
| نسخة المفتاح | نسختان في مكانين منفصلين، بمسؤولين مختلفين |
| تدوير المفتاح | سنويًا أو عند مغادرة مسؤول |
| التحقق | `sha256sum` لكل نسخة + `restic check` أسبوعيًا |
| الوصول | مستخدم `backup` فقط يقرأ، ومستخدم `restore` منفصل |

**ممنوع:** كلمة مرور النسخ في سكربت نصي مكشوف، أو مفتاح التشفير على نفس NAS.

## 4. أوامر مرجعية

### 4.1 Full Logical

```bash
mysqldump \
  --defaults-extra-file=/etc/smart-hospital/backup.cnf \
  --single-transaction --routines --triggers --events \
  --set-gtid-purged=OFF \
  smart_hospital \
  | gzip -9 \
  | gpg --encrypt --recipient backup@hospital.local \
  > /backup/staging/smart_hospital_$(date +%F_%H%M).sql.gz.gpg
```

### 4.2 Binlog

```bash
mysqlbinlog --read-from-remote-server --host=127.0.0.1 \
  --user=sh_backup --password=<...> \
  --raw --stop-never mysql-bin.000001 \
  --result-file=/backup/staging/binlog/
```

> في الإنتاج يُدار Binlog Shipping كخدمة/مهمة مجدولة مع مراقبة التأخر. لا تعتمد على نسخ يدوي.

### 4.3 Restic

```bash
export RESTIC_REPOSITORY=sftp:backup@nas.hospital.local:/backups/restic
export RESTIC_PASSWORD_FILE=/etc/smart-hospital/restic.pass

restic backup /backup/staging /opt/smart-hospital/app/config /opt/smart-hospital/releases
restic check --read-data-subset=5%
restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune
```

### 4.4 التحقق

```bash
sha256sum /backup/staging/*.gpg > /backup/staging/SHA256SUMS
gpg --decrypt file.sql.gz.gpg | gunzip | head
restic snapshots
```

## 5. سيناريوهات الاستعادة

### R1 — فقدان الخادم بالكامل

| الخطوة | الأمر/الإجراء | الزمن التقديري |
|---|---|---|
| 1 | تجهيز خادم جديد (نفس الإصدارات) | 30–60 دقيقة |
| 2 | تثبيت OS + MySQL + GlassFish + Nginx | 45–90 دقيقة |
| 3 | استعادة آخر Full | 15–45 دقيقة |
| 4 | تطبيق Binlogs حتى آخر لحظة | 10–30 دقيقة |
| 5 | استعادة Config + EAR + المرفقات | 10–20 دقيقة |
| 6 | تشغيل الخدمات + Smoke Tests | 15–30 دقيقة |
| 7 | التحقق من الأعداد والتدقيق | 10–20 دقيقة |
| **الإجمالي** | | **2.5–4 ساعات** |

**قاعدة:** لا تُعلن العودة قبل نجاح `health/ready` + التحقق من عدد السجلات + فحص سلسلة التدقيق.

### R2 — حذف/تلف بيانات (PITR)

1. أوقف الكتابة على النظام (وضع الصيانة) أو اعزل الجداول المتأثرة.
2. استعد نسخة Full إلى **قاعدة مؤقتة** (`smart_hospital_restore`) — لا فوق الإنتاج.
3. طبّق Binlogs حتى اللحظة قبل الحادث (`--stop-datetime`).
4. قارن الأعداد/البصمات مع الإنتاج.
5. بعد الموافقة (شخصان)، انقل البيانات أو استبدل القاعدة.
6. أعد تشغيل التطبيق وتحقق.
7. وثّق الحادث والسبب.

**ممنوع:** PITR مباشرة على قاعدة الإنتاج دون نسخة احتياطية من الحالة الحالية.

### R3 — استعادة جدول واحد

1. استخرج الجدول من Full إلى قاعدة مؤقتة.
2. راجع الفروقات.
3. استخدم `INSERT ... SELECT` أو `pt-table-sync` بعد موافقة.
4. تحقق من القيود والفهارس.

### R4 — المرفقات

1. استعد من Restic إلى مسار مؤقت.
2. تحقق من `sha256` لكل ملف مقابل `attachments.sha256`.
3. انقل الملفات الناقصة فقط (لا تستبدل الكل).
4. أعد فحص عينات.

### R5 — فدية/اختراق

1. **اعزل** الخادم عن الشبكة فورًا.
2. لا تدفع، لا تحذف، لا تعد تشغيل من النسخة المصابة.
3. استعد من نسخة Offline/Immutable.
4. غيّر كل كلمات المرور والمفاتيح والشهادات.
5. راجع `audit_logs` و`login_attempts` و`access_logs`.
6. أبلغ الإدارة/الجهة المختصة حسب السياسة.
7. لا تعد الإنتاج قبل تحقيق مكتمل.

### R6 — نسخة تالفة

1. `sha256sum -c` و`gpg --decrypt` و`restic check`.
2. استخدم النسخة السابقة.
3. أبلغ عن العطل وأصلح السبب.
4. لا تحذف النسخ القديمة حتى تنجح استعادة بديلة.

## 6. التحقق الدوري

| الاختبار | التكرار | معيار النجاح | المسؤول |
|---|---|---|---|
| فحص سلامة النسخة | يوميًا | Checksum + فك تشفير | Backup Operator |
| استعادة آلية إلى TEST | أسبوعيًا | DB تعمل + أعداد مطابقة ±0 | DBA |
| تمرين استعادة كامل | ربع سنوي | RTO ≤ 4 ساعات + تقرير | DBA + IT |
| فحص Binlog Lag | كل 15 دقيقة | ≤ 5 دقائق | Monitoring |
| مراجعة صلاحيات النسخ | شهريًا | لا وصول غير مصرح | Security |
| اختبار Offline Copy | شهريًا | يمكن القراءة | Backup Operator |

**سجل التمرين:** التاريخ، النسخة، الزمن الفعلي، المشاكل، الإجراء التصحيحي، التوقيع.

## 7. المراقبة والتنبيهات

| المؤشر | الحد | التنبيه |
|---|---|---|
| آخر Full ناجح | > 26 ساعة | Critical |
| آخر Binlog | > 15 دقيقة | Critical |
| فشل مهمة نسخ | أي | High |
| مساحة NAS | > 80% | High |
| مساحة Staging | > 80% | High |
| فشل Checksum | أي | Critical |
| فشل `restic check` | أي | High |
| نسخة Offline متأخرة | > 8 أيام | Medium |

**قاعدة:** تنبيه النسخ يذهب إلى شخص محدد، لا إلى بريد عام.

## 8. الأدوار

| الدور | المسؤولية |
|---|---|
| Backup Operator | تشغيل ومراقبة النسخ اليومية |
| DBA | الاستعادة، PITR، التحقق |
| IT Manager | اعتماد التمرين وخطة التعافي |
| Security Officer | مراجعة الوصول والتشفير وحوادث الفدية |
| Owner | اعتماد RPO/RTO والسياسة |

**فصل المهام:** من يشغّل النسخ لا يعتمد نتيجة التمرين وحده. استعادة الإنتاج تحتاج موافقة شخصين.

## 9. خطة التعافي (DR Runbook) — ملخص

```text
T+0      اكتشاف العطل
T+5      إعلان حادث + عزل إن لزم
T+15     تحديد السيناريو (R1..R6)
T+30     تجهيز البيئة البديلة/المؤقتة
T+60     استعادة Full
T+90     تطبيق Binlogs
T+120    استعادة Config/EAR/Attachments
T+150    تشغيل + Smoke Tests
T+180    تحقق البيانات + سلسلة التدقيق
T+240    إعلان العودة أو تصعيد
```

**معايير العودة:** Health Ready + أعداد مطابقة + تدقيق سليم + موافقة المالك/IT.

## 10. معايير القبول

- [ ] Full يومي يعمل وينتج ملفًا مشفّرًا.
- [ ] Binlog يُنقل كل ≤ 15 دقيقة مع مراقبة التأخر.
- [ ] نسخة خارج الخادم (NAS) ونسخة Offline أسبوعية.
- [ ] استعادة كاملة إلى TEST ناجحة أسبوعيًا.
- [ ] تمرين ربع سنوي يحقق RTO ≤ 4 ساعات.
- [ ] RPO مُقاس فعليًا ≤ 15 دقيقة.
- [ ] المفاتيح محفوظة خارج الخادم وبنسختين.
- [ ] لا وصول لمستخدم التطبيق إلى نسخ الاحتياطي.
- [ ] سجل تمرين موقّع ومتاح للمراجع.
